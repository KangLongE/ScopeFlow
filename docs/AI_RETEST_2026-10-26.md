# AI 분석·변경 비교 수정 및 검증 (2026-10-26)

## 재현 조건과 성공 기준

최초 분석은 사용자가 제공한 다음 원문을 변경하지 않고 사용했다.

> 카페 소개 웹사이트를 만들어주세요. 모바일과 PC에서 사용할 수 있는 소개 페이지 1개와 메뉴 목록이 필요합니다. 결제, 회원가입, 관리자 페이지, 외부 서비스 연동은 제외합니다. 로고와 메뉴 자료는 고객이 제공합니다. 예산은 100만원입니다.

변경 비교는 위 조건으로 만든 격리된 로컬 승인 Scope를 기준으로 했다. 기준 견적은 660,000원, 기간은 8일이며 운영 프로젝트의 계약이나 데이터를 사용하지 않았다. 변경 문구는 다음과 같다.

> 기존과 같은 1페이지 내부에 외부 지도 iframe 위젯을 추가해주세요. 이번 지도 추가를 위해 외부 서비스 연동 개발 제외 항목만 해제해주세요. 결제, 회원가입, 관리자 페이지 제외와 고객 자료 제공 조건은 유지합니다.

성공 기준은 비어 있지 않은 일반 검토 초안 생성, 1페이지·예산·제외·자료 제공 조건 보존, 실제 JSON 필드에 연결되는 숫자 참조, 서버 재검증 통과, 추가 기능 승인 시 관련 Scope 항목 동시 반영이다. 같은 페이지 조건과 근거의 확인은 단계가 바뀌어도 재사용하고, 관련 구조나 근거가 바뀌면 만료해야 한다.

## 변경 내용

- Groq 요청에서 중복된 원문과 내부 감사 이력을 제외한다. 모든 근거 원문과 승인 Scope의 범위·숫자는 보존한다. 고객 연락처는 모델 입력에서 제외한다. 변경 비교는 승인된 기준 문서를 사용한다.
- `AI_REQUEST_TOKEN_BUDGET`의 기본값을 8,000으로 두고, 직렬화한 입력·스키마·프롬프트 크기로 출력 상한을 계산한다. 원문을 임의로 자르지 않으며 최소 출력 공간이 없으면 전송 전에 중단한다. 기존 `.env` 파일은 수정하지 않았다. 계정 한도에 맞춰 서버에서 예산을 조정할 수 있다.
- 구조화 응답의 `reviewNotes` 위치와 승인된 제외 항목 제목을 명시한다. OSS 모델에는 낮은 reasoning effort와 reasoning 제외 옵션을 사용한다. 잘린 JSON은 반영하지 않는다.
- 실제로 관찰한 두 가지 구조 오류만 서버에서 정리한다. 루트에 잘못 놓인 알려진 검토 배열을 `reviewNotes`로 이동하고, 현재 승인된 제외 항목의 알려진 ID를 정확한 제목으로 연결한다. 누락된 사실을 만들거나 충돌하는 값을 선택하지 않는다. 전체 스키마·공통 규칙 검증은 계속 적용한다. 원본 응답과 복구 감사 기록을 보존하며, 제공자 토큰 사용량이 없는 경우 비용을 무료로 표시하지 않는다.
- 숫자 참조는 모델에 경로를 작성시키지 않고 실제 결과의 숫자 필드에서 생성한다. 저장 후 재검토에도 경로를 갱신한다. 설명 문장에 적힌 잘못된 숫자를 자동으로 고쳐 검사를 면제하지 않는다.
- 승인된 추가 기능은 새 Scope 버전의 포함 기능·외부 연동·납품 범위에 함께 반영한다. 이전 승인 문서는 변경하지 않는다.
- 페이지 확인 기록은 기능 설명·페이지 구조·관련 고객 근거·규칙 버전에 연결한다. 단계나 배열 인덱스, 무관한 원문 리비전 때문에 다시 묻지 않는다. 관련 조건 변경과 명시적인 별도 페이지 요구는 다시 검증한다.

## 실제 Groq 요청: 총 2회

사용자의 절대 상한을 지켰다. 각 호출 전에 입력 원문·승인 기준·구조화 스키마·토큰 예산을 검증했으며 자동 재시도는 하지 않았다. 모델은 `openai/gpt-oss-120b`이다.

| 요청 | 추정 입력 토큰 | 출력 상한 | 실제 응답 | 수정 후 동일 응답 재생 |
| --- | ---: | ---: | --- | --- |
| 최초 분석 | 4,364 | 2,600 | HTTP 400 `json_validate_failed`: 검토 배열이 루트에 배치됨 | 일반 분석 초안 생성, 검증 통과 |
| 변경 비교 | 6,400 | 1,600 | HTTP 400 `json_validate_failed`: 검토 근거 배열 위치 및 제외 항목 ID 표현 오류 | 일반 비교 초안 생성, 숫자 참조 8개, 검증 통과 |

두 요청에서 토큰 한도 오류는 발생하지 않았다. 응답 헤더의 분당 토큰 한도는 8,000이었다. 위 입력 수치는 사전 추정값이며 실제 토큰 수와 같다는 보장은 없다. 계정의 공유 사용량도 별도 영향을 준다. 출력 상한 조절과 입력 중복 제거는 한도 초과 가능성을 줄이지만 모든 크기의 요청이나 계정 상황을 보장하지 않는다. 긴 원문은 보존한 채 전송 전 중단할 수 있으며 수동 검토가 가능하다.

**최종 수정 코드로 새 Groq 응답을 다시 받는 검증은 하지 않았다.** 허용된 두 요청을 모두 사용한 후, 저장한 실제 응답을 네트워크 대역으로 재생해 검증했다. 실패한 HTTP 응답을 라이브 HTTP 200 성공으로 집계하지 않았다. 로컬 브라우저 검증 서버에서도 Groq 외부 전송을 차단했다.

## 검증 결과

- Backend 테스트 64개 통과, 건너뜀 없음. 격리 PostgreSQL에서 승인·불변 문서·검토 리비전·확인 만료·납품 범위 갱신을 검증했다.
- Frontend 테스트 14개 통과. 양쪽 빌드·타입 검사·lint 통과.
- 로컬 브라우저에서 최초 분석과 변경 비교의 일반 검토 양식을 확인하고 각각 저장·서버 재검증을 실행했다. 둘 다 오류 0·경고 0·검토 필요 0으로 통과했다. 변경 기능 시간은 Frontend 4 / Backend 2 / Design 2 / QA 1시간, 일정 영향은 2일로 유지됐다.
- 제외 항목 제안은 계속 담당자 검토를 거친다. 모델이 추출했다는 이유로 고객 확정 조건으로 승격하지 않는다. 기존 Credit 예약·차감 정책도 유지한다.
- 긴 이력의 신선도 검사는 모의 제공자와 테스트 전용 32,000 예산을 사용한다. 해당 테스트 통과가 모든 긴 이력이 기본 8,000 예산에 들어간다는 의미는 아니다. 기본 예산 초과의 전송 전 차단은 별도 테스트로 검증했다.
- 재현 메타데이터·원본 응답·화면 증거·테스트용 로그인 정보는 Git에서 제외된 로컬 테스트 경로에만 보관했다. 화면의 테스트 Credit 사용량에는 모의 실행과 저장 응답 재생이 포함되며 실제 Groq 요청 횟수나 청구액이 아니다.
- 운영 DB·배포 환경은 변경하지 않았다. 새 의존성과 DB 마이그레이션은 없다. 이 작업에서 커밋·푸시·배포는 실행하지 않았다.

구조화 응답과 모델 옵션은 [Groq Structured Outputs](https://console.groq.com/docs/structured-outputs), [Reasoning](https://console.groq.com/docs/reasoning), [Rate Limits](https://console.groq.com/docs/rate-limits)를 참고했다.
