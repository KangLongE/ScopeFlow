# ScopeFlow AI 결과 규칙 검증 구현·검증 기록

작성일: 2026-10-07. 기준: `ScopeFlow-AI-Rule-Validator-Spec.md` 및 기존 AI Context Pipeline.

## 구현

- 기존 Context builder·fingerprint·견적 계산·권한·승인 트랜잭션을 재사용했다. 추가 검증 AI, 외부 규칙 엔진, 관리자 규칙 편집기, 새 계산 정책은 도입하지 않았다.
- `Backend/src/lib/ai/rule-validator.ts`의 `validateAIResult`는 DB 접근·AI 호출·후보 수정 없이 RV-001~014를 검사한다. 결과는 `blocked`, `review_required`, `passed`, `passed_with_warnings`다. 검증 예외는 RV-000으로 확정을 차단한다.
- AI 최초 결과, 담당자 검토 저장, 최종 반영, 견적/Scope 수정, 고객 승인 링크 발급, 고객 승인 및 새 Scope 생성에 공통 검증을 연결했다. 전달받은 `validation`·면제 플래그는 신뢰하지 않는다.
- 파싱 가능한 잘못된 결과는 원본과 검토 후보를 분리해 저장한다. 파싱 불가능한 응답은 실패 실행의 `rawResponse`에 보존한다. 재검증은 AI를 호출하거나 Credit을 차감하지 않으며 Groq 자동 재시도도 제거했다.
- 구조화된 구현 속성은 페이지 수·별도 페이지·서버 작업 종류·기능 유형·자료 제작/적용을 구분한다. 조건 기준은 저장된 고객 근거와 승인 Scope다. 중요한 속성이 없거나 근거가 충돌하면 담당자 보완이 필요하다.
- 회사 단가 스냅샷으로 계산 금액을 검증하고, 사유가 있는 최종 금액 조정은 구분한다. 기간은 담당자 확정 기간에 변경 승인 일수를 더한다. 시간을 8로 나누어 일수로 강제하지 않으며 기준 완료일이 없으면 날짜를 만들지 않는다.
- 경고 확인은 항목별 사유·확인자·시점·후보 리비전·Context·규칙 버전과 연결한다. 관련 값/근거가 바뀐 확인은 만료되며, 과거 값으로 되돌려도 자동 부활하지 않는다. 무관한 항목의 확인과 과거 검토 이력은 보존한다.
- 원본 AI 응답, 후보 리비전, 변경 필드, 검증 결과, 경고 확인을 AI 실행 및 감사 이력에 기록한다. 고객 문서에는 내부 검증 로그를 노출하지 않는다. 이미 승인된 Scope는 변경하지 않는다.

## 검토 화면 및 API

- 기존 AI/변경 검토 화면에 상태·이슈 개수·필드별 안내·출처 근거·수정 방향·경고 사유/확인·서버 재검증을 추가했다. 수정 즉시 이전 통과 상태를 무효화한다.
- 늦은 저장 응답은 새 입력을 통과 상태로 만들지 않는다. 현재 입력과 스크롤을 보존하고, 확정 거부 시 첫 문제 필드로 이동한다. 오류 후보·복잡한 구조/근거는 원본과 구분된 JSON 검토 편집으로 보완할 수 있다.
- `ai.review`, `ai.apply`, `estimate.review`, `scope.review`, `change.saveDraft`, `change.review` 및 일반 견적/Scope 수정은 `candidateRevision`을 요구한다. 최초 리비전은 0이고 이후에는 저장 응답의 값을 사용한다. 프론트는 서버 리비전을 전송한다.
- 리비전 또는 실제 Context/기준 Scope 변경은 409, 최종 검증 거부는 422 `AI_RESULT_VALIDATION_FAILED`와 `error.validation`이다. 프론트 명령 프록시는 이를 응답의 `validation`으로 폼에 전달한다. 검토 저장은 이슈가 있어도 성공할 수 있지만 통과 전 확정·승인은 불가하다.
- 저장 Context가 있는 기존 초안은 최신 규칙으로 재검증한다. 프롬프트 버전만 바뀌었다면 추가 유료 호출을 요구하지 않는다. Context가 없거나 실제 근거가 바뀌었다면 기존 409/재분석 정책을 적용한다.

DB 통합 테스트는 고정 이름의 별도 로컬 DB만 허용하는 `Backend/scripts/ux-check.mjs test`로 실행했다. 테스트는 고정 응답을 사용하며 실제 Groq와 운영 DB를 사용하지 않는다. `pg`의 동시 query 사용에 관한 deprecation 경고는 관찰됐으나 테스트 실패는 없었다.

실제 브라우저에서는 가입·Workspace/프로젝트 생성 후 고정 AI 견적 후보를 검토했다. QA 8→7 저장 요청을 지연시킨 동안 6으로 다시 수정했고, 이전 통과 응답 이후에도 입력 6과 재검증 필요 상태·확정 비활성화가 유지됐다. 설명 유지 경고를 항목별 확인한 뒤 최종 반영해 DB의 QA 6과 초안 제거를 확인했다. 조작된 직접 요청의 422 및 검증 정보 전달도 확인했다. 1440×1000/390×844 화면에서 가로 넘침과 브라우저 실행 오류가 없었다.

브라우저 보조 스크립트·스크린샷·로컬 PostgreSQL은 ignored `test-results` 안에 보관했다. 고정 규칙 및 DB 회귀 테스트는 아래 추적 파일에 남겼다.

## 적용 사항 및 한계

- `0003_ai_context`와 `0004_ai_rule_validation` migration 및 Prisma client 재생성이 필요하다. 로컬 격리 DB 적용/생성은 확인했다. 운영 DB migration, Vercel 환경변수/배포, 커밋·푸시는 이번 요청에서 수행하지 않았다. 운영 대상과 백업을 확인한 후 `Backend`에서 `npm run db:deploy`하고 두 프로젝트를 배포해야 한다.
- 실제 Groq 응답 품질·호환성/비용과 배포 환경의 승인 흐름은 이번 고정 회귀/로컬 브라우저 검사에 포함하지 않았다.
- 자유 문장 숫자/키워드 검사는 제한된 휴리스틱이다. 자동 계약 해석·견적 시장 적정성 판정은 하지 않는다. 중요한 조건은 구조화된 속성과 확정 출처가 있어야 검사 가능하며 부족하면 검토가 필요하다.
- 기본 폼으로 표현되지 않는 복잡한 자료·숫자 출처 연결은 검토 JSON 편집을 사용한다. 내부 기록을 고객 페이지에 노출하는 검증 대시보드는 추가하지 않았다.
