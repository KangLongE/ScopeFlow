# 변경 승인 금액·기간 표시 구현 및 검증

작성일: 2026-10-13. 기준: `ScopeFlow-Change-Approval-Impact-Spec.md`.

## 구현 결과

- 고객 승인 대기·완료·담당자 변경 검토에서 공통 `ChangeImpactSummary`와 형식화 함수를 사용한다. 기존/이번 변경/결과의 금액과 예상 개발 기간을 함께 보여주며, 승인 버튼 근처에도 같은 서버 결과의 요약 문장을 표시한다.
- 기존 금액은 연결된 승인 Scope의 최종 `estimate.total`, 변경 금액은 담당자가 확정한 `change.amount`다. AI 원본·계산 견적·최신 대시보드를 기준으로 합산하지 않는다. 합계는 Backend가 계산한다.
- 기존 800,000원 +140,000원 → 940,000원, 기간 8일 +1일 → 9일을 확인했다. 완료일이 없으면 미정 그대로다. 기존 날짜 정책은 `addDays`의 UTC 달력일 추가이며 영업일/휴일 정책을 추가하지 않았다. 날짜 전용 값은 그대로 표시한다.
- 금액 null/누락/형식 오류는 확인 필요이며 0으로 바꾸지 않는다. 기간 미정·추가 일수 미정·0일을 구분한다. 변경 후 데이터 불일치와 기준 Scope 변경은 승인 보류와 담당자 재검토로 표시한다.
- 승인 전에는 ‘승인 시’, 완료 후에는 ‘승인된 값’과 서버가 생성한 실제 Scope 버전을 표시한다. 재검토 상태는 ‘당시 비교값’으로 표시해 승인 가능한 확정액처럼 보이지 않게 했다. 총 견적은 미납액/현재 결제액이 아니라는 안내를 추가했다. 기존 의견 선택·동의 절차를 유지하고 새 확인 단계는 추가하지 않았다.

## 서버·저장 계약

- 기존 `client_access_tokens`에 nullable `approvalSnapshot` JSON 한 필드만 추가했다. 새 승인 테이블은 없다. `0005_change_approval_impact` migration이 필요하다.
- 새 변경 승인 링크는 발급 당시 공개용 요청/기능 목록/금액·기간 요약, 기준 Scope fingerprint 및 변경 대상 fingerprint를 저장한다. 조회는 이 스냅샷을 사용하며 이후 초안 수정으로 당시 값을 교체하지 않는다.
- 고객 응답 `change.impact`에는 기준/결과 Scope 식별 정보, 금액 before/delta/after, 기간 beforeDays/deltaDays/afterDays, 완료일 상태, `canApprove`, 차단 사유, 승인 대상 식별자/리비전이 포함된다. 회사 단가·AI 원본·출처 ID·내부 검증 로그·fingerprint는 새 고객 요약 응답에 노출하지 않는다.
- 변경 승인 및 의견 요청은 `target: { approvalSnapshotId, changeRequestId, revision }`을 전송한다. 누락은 422, 다른 대상/리비전은 409다. 승인 시 기준 Scope, 스냅샷, 현재 상태와 공통 Rule Validator를 다시 검사한다. Frontend가 보낸 before/delta/after는 저장 근거로 사용하지 않는다.
- 승인 문서의 총액/기간/완료일은 검증된 서버 요약을 사용해 기존 트랜잭션에서 생성한다. 중복 요청은 한 번만 반영된다. 처리 후 재조회는 동일 영수증과 당시 요약을 보여준다. 기존 만료·회수·중복 제출 정책을 유지했다.
- 과거 스냅샷이 없는 기록은 정확한 `baseScopeId`와 저장된 확정 변경 기록으로만 재구성한다. 최신 Scope로 과거 기준을 채우지 않는다. 기준/값이 없거나 잘못되면 확인 필요로 표시하고 승인하지 않는다. 과거 승인 Scope는 수정하지 않는다.
- 담당자 초안 저장 응답에도 동일 구조의 요약을 포함한다. 입력 수정/재검증 중에는 이전 합계를 숨기며, 기존 리비전/입력 일치 검사로 늦게 도착한 요약을 최신 수정값처럼 표시하지 않는다.
- 고객 조회 실패 시 금액이나 승인 폼을 표시하지 않고 실제 재조회 링크를 제공한다. 승인 응답을 받지 못하면 상태 조회로 완료 여부를 확인하는 복구 경로를 추가했다.

단위 회귀: `Backend/tests/change-impact.test.ts`, `Frontend/tests/change-impact.test.ts`.
실제 DB/HTTP 승인 회귀: `Backend/tests/impact-integration.test.ts` 및 기존 Context/Rule Validator/승인 통합 테스트.

브라우저에서는 발급된 800,000원/+140,000원/940,000원 및 8일/+1일/9일, 완료일 미정을 확인했다. 프론트 프록시 POST와 Backend 승인 POST 모두 200이었고, 같은 링크에서 승인 완료·Scope v1.1과 재승인 폼 제거를 확인했다. 새로고침 후에도 같은 값이었다. 화면을 375px로 바꾸어 세 값의 세로 배치와 가로 넘침 없음, 키보드 폼 이동/선택을 확인했다. 브라우저 error/warn 로그는 없었다.

스냅샷 불일치 검증에서는 발급 당시 요약이 그대로 유지되는 동시에 `canApprove=false`, 승인 버튼 비활성화, 담당자 재검토 안내가 표시됐다. 검증용 Backend만 중지해 조회 실패를 재현했고, 임시 0원·0일이나 승인 폼 없이 재시도 링크가 표시됐다. Backend 복구 후 링크를 눌러 같은 스냅샷의 재검토 상태로 돌아왔다.

보조 fixture·스크린샷은 ignored `test-results`에 보관했다. 실제 계약·운영 DB·Groq 호출은 사용하지 않았다. 담당자 화면은 공통 컴포넌트/형식화 함수 및 서버 응답 일치로 검사했으며, 이번 브라우저 세션에서 실제 사용자 계정의 담당자 화면에 로그인하지 않았다.

## 운영 적용과 미실행 범위

- `0005_change_approval_impact`는 격리된 로컬 테스트 DB에만 적용했다. 이전 작업의 `0003_ai_context`, `0004_ai_rule_validation`이 미적용이면 함께 필요하다. Prisma client 재생성은 수행했다.
- 운영 DB migration, Vercel 배포·환경변수 변경, 커밋·푸시는 실행하지 않았다. 운영 대상과 백업 확인 후 Backend의 `npm run db:deploy`, 두 프로젝트 배포가 필요하다.
- 실제 모델 호출이나 추가 Credit 비용, 결제·청구 기능, 새 휴일/영업일 계산 및 승인 단계는 추가하지 않았다. 운영 환경 E2E 및 실제 음성 스크린리더/브라우저 패킷 손실 테스트는 별도다.
- 격리 통합 검사에서 현재 Prisma/pg 연결의 동시 query 관련 deprecation 경고가 출력됐다. 검사 실패는 없었으며 이번 작업에서 드라이버 교체나 pg 9 업그레이드는 하지 않았다.
