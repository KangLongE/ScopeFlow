# 변경 비교 토큰 한도 오류 조사·수정 (2026-11-02)

## 확인된 원인

사용자가 보고한 오류는 `AI_PROVIDER_RATE_LIMITED`(429), `AI_CONTEXT_TOO_LARGE`(413)와 Groq 분당 토큰 한도 안내다. 고객 요청 내용의 업무 규칙 검증 실패와는 별개의 제공자 입력·사용량 한도 문제다.

운영 AI 사용량 화면에서 2026-11-02의 실패한 Scope 비교가 `openai/gpt-oss-120b`, 프롬프트 `3.2-post-push-retest`로 실행된 것을 확인했다. Vercel의 현재 Production 백엔드도 `d5dc5886a9b2295c142d39741e34c06290b2c2ec`(2026-10-19)였다. 10월 26일의 토큰 예산·구조 복구 수정은 로컬 변경에 남아 있었다.

해당 운영 코드에는 다음 문제가 있다.

- 비교 입력에 승인 Scope 외의 중복 데이터·이력이 포함된다.
- 입력 크기와 관계없이 출력 상한을 기본 6,000토큰으로 설정한다.
- 같은 조직에서 앞서 실행한 분석도 제공자의 분당 사용량을 소비한다. 한 번의 요청이 들어갈 수 있어도 연속 실행에는 한도가 부족할 수 있다.
- 단일 요청 자체가 전체 허용량보다 큰 경우와 일시적인 공유 한도 소진의 안내가 충분히 구분되지 않는다.

제공자가 보낸 정확한 운영 `Limit / Used / Requested / Retry-After` 수치는 이번에 확보하지 못했다. 연결된 Vercel MCP에서 프로젝트를 읽을 수 없고, 브라우저의 런타임 로그는 로그인 화면으로 이동했다. 운영의 한도 수치나 대기 시간을 추정해 확정하지 않았다.

## 수정

- 기존 미배포 수정의 비교 입력 정리·요청별 토큰 예산 계산을 검증했다. 승인 기준과 모든 고객 원문·저장 답변 근거는 보존한다. 예산에 맞지 않으면 제공자 전송 전에 중단하며 원문을 임의로 자르지 않는다.
- 기본 요청 예산 8,000 내에서 입력·스키마·프롬프트의 직렬화 크기를 고려해 출력 상한을 정한다. 비교의 출력 상한은 최대 2,600이며 최소 출력 공간도 확보할 수 없으면 `AI_CONTEXT_TOO_LARGE`로 처리한다.
- Groq가 429로 응답해도 `Requested > Limit`인 단일 요청 초과는 `AI_CONTEXT_TOO_LARGE`로 분류한다. 같은 요청을 기다렸다 반복하는 것이 해결책인 것처럼 안내하지 않는다.
- 일시적인 429는 같은 조직의 공유 한도임을 알리고, 유효한 `Retry-After`가 있으면 올림한 초 단위 대기 안내를 보여준다. 헤더가 없거나 잘못된 값이면 시간을 만들지 않는다. 자동 재시도는 추가하지 않았다.
- 진단 기록은 `limit`, `used`, `requested`, `retryAfterSeconds`, 입력 추정치와 출력 상한을 보존한다. 고객 원문·API 키·제공자의 원문 오류 메시지는 로그에 출력하지 않는다.
- 실패 시 Credit 미차감, 기존 초안 보존, 수동 검토 계속하기 동작을 유지한다. 제공자 한도와 서비스 Credit 잔여량은 별개다.

## 같은 저장 응답을 사용한 대조 검증

10월 26일 격리 테스트에 저장된 변경 비교 입력과 실제 Groq 실패 응답을 사용했다. 기존 커밋의 Provider·모델 스키마·프롬프트와 현재 수정 코드를 같은 입력에 적용했다. 외부 fetch는 모의 응답으로 대체했다.

| 항목 | 기존 배포 코드 | 수정 코드 |
| --- | ---: | ---: |
| 추정 입력 토큰 | 7,914 | 6,541 |
| 출력 상한 | 6,000 | 1,459 |
| 추정 합계 | 13,914 | 8,000 |
| 저장된 실제 구조 오류 응답 처리 | `AI_INVALID_RESPONSE` | 일반 비교 초안·검증 통과 |
| 실제 숫자 필드 참조 | 모델 결과에 의존 | 서버 생성 8개 |

토큰 수는 `UTF-8 bytes / 3 + 256` 기반 사전 추정값이며 제공자의 실제 과금·토큰 수는 아니다. 429 상황을 실제로 재현하려고 새 요청을 보내지 않았다. 조직의 현재 잔여 토큰은 별도이므로, 8,000 예산이 모든 동시·연속 요청의 성공을 보장하지 않는다.

검증 결과:

- Backend 67개 테스트 통과, 건너뜀 없음. 격리 PostgreSQL에서 Credit 예약 해제·실행 중복 방지·원문 보존·승인 문서 불변성을 포함해 검사했다.
- Frontend 14개 테스트 통과. 기존 오류 메시지가 표시되고 과금 없는 수동 검토를 계속할 수 있는지 확인했다.
- 양쪽 Production 빌드 및 빌드에 포함된 TypeScript 검사·lint 통과.
- 비교의 실제 wire 스키마·입력 보존·출력 예산, 전송 전 초과 차단, 429/413 구분, `Retry-After` 안내, 자동 재호출 없음에 대한 회귀 검사를 추가했다.
- 이번 조사·검증의 실제 Groq 요청은 **0회**다. 이전에 허용받은 두 요청을 모두 사용한 상태를 유지했다.
- 운영 데이터의 변경 비교 재실행·승인·수정, DB 마이그레이션, 환경변수 변경은 수행하지 않았다.

운영 해결에는 검증된 변경의 커밋·푸시와 Frontend/Backend 재배포가 필요하다. 로컬 검증 성공과 운영 반영 완료는 구분한다.

참고: [Groq Rate Limits](https://console.groq.com/docs/rate-limits)는 조직 단위 한도, 실제 계정 한도 확인, 429 및 `Retry-After`·잔여 토큰 헤더를 설명한다.
