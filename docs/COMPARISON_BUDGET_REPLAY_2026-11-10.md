## 원인과 수정

기존 추정식은 전체 HTTP JSON의 UTF-8 크기를 사용했다. 메시지 `content` 안의 JSON은 실제 메시지 문자열로 한 번 전달되지만 HTTP 직렬화에서 따옴표·역슬래시·개행이 다시 이스케이프된다. 이 바깥 직렬화의 추가 바이트까지 모델 입력으로 계산했다. Groq의 입력 계약은 메시지 목록과 메시지 내용이다. [공식 API 문서](https://console.groq.com/docs/api-reference)

문자열 메시지의 바깥 이스케이프 바이트만 크기 추정에서 제외했다. 메시지 자체의 JSON 표현·고객 원문·프롬프트·응답 스키마·기타 요청 필드는 바꾸지 않았다. 기존 UTF-8 크기 기반 추정과 256 여유분, 요청 예산 8,000, 응답 최소값 1,024, 출력 설정 6,000을 유지한다. 환경변수는 변경하지 않았다.

사전 차단 진단에는 남은 공간·최소 출력·최종 출력 상한·HTTP 크기·바깥 이스케이프 크기를 추가했다. 같은 숫자를 런타임 경고에도 남기며 원문·키·제공자 비밀은 출력하지 않는다.

## 동일 운영 입력 재생

운영 실패 입력을 로컬 ignored 파일에 보관하고 현재 Provider에 그대로 전달했다. 연락처만 조회 단계에서 제외했으며 기존 Provider도 모델 전송 전에 동일한 연락처를 제거하므로 실제 wire 입력에는 차이가 없다. 기존 추정식으로 6,992가 정확히 재현되는 것을 확인한 뒤 수정식을 적용했다.

| 항목 | 기존 | 수정 |
| --- | ---: | ---: |
| 추정 입력 | 6,992 | 6,671 |
| 응답 상한 | 1,008: 사전 차단 | 1,329: 사전 검사 통과 |
| 예산 | 8,000 | 8,000 |
| 출처 | 13 | 동일한 13개 |

모든 wire 필드, 출처 본문·종류·리비전을 동일성 검사했다. 승인 Scope v1.0의 800,000원·8일·제외 항목 5개도 보존됐다. 전송은 모의 fetch로 가로채고 이전에 저장한 형식 오류 응답을 재생했다. 미완성 초안 처리까지 도달하며, 원래 응답의 `IN_SCOPE`·추가 기능/시간 모순은 `RV-003`으로 계속 차단된다. 이번 수정으로 모순을 정상 결과로 승인하지 않는다.

Backend 72개 테스트가 건너뜀 없이 통과했다. 이스케이프 때문에 발생하던 경계값 오차, UTF-8, 큰 응답 스키마, 출력 설정 상한, 실제 초과 요청 전송 차단 및 안전한 진단 기록을 검사했다. TypeScript·lint·Production 빌드도 확인했다.

실제 Groq 요청은 **0회**이며 운영 DB 쓰기·AI 재실행은 하지 않았다. 수치는 여전히 로컬 휴리스틱 추정이지 제공자의 실제 토큰 수가 아니다. 실제 제공자 응답과 조직의 공유 한도 여유는 이번 재생만으로 확인할 수 없다. [공식 한도 문서](https://console.groq.com/docs/rate-limits)
