# 변경 비교의 필수 검토 배열 누락 수정 · 2026-11-03

## 확인한 실패

운영 프로젝트 `eaff7305-ad9c-4162-b718-324df81580ef`의 실행 `f2be058c-c0e9-41cd-bbf7-491f807a77db`는 2026-11-03 14:27 KST에 실패했다. 배포 `82b9a46`, 비교 프롬프트 `3.4-compact-comparison`을 사용했다.

운영 DB에서 읽기 전용으로 확인한 2,546자 원본은 정상 JSON이지만 `reviewNotes.sourceRefs`, `reviewNotes.unresolvedItems`, `reviewNotes.proposedChanges`를 생략했다. 세 필드 모두 Zod `invalid_type`에 해당하며, 기존 위치 이동 복구로는 처리할 수 없었다. `IN_SCOPE` 판정과 신규 지도 기능·제외 해제·추가 작업 4시간도 모순된다. 이 모순은 `RV-003`의 차단 대상이다.

운영 기록에는 원래 제공자의 HTTP 상태·오류 코드·응답 사용량이 보존되어 있지 않다. 이번 재생에서 사용한 HTTP 400 `json_validate_failed`는 모의 상태이며, 실제 운영 HTTP 상태를 확정한 것은 아니다.

## 변경

- 비교 전용 wire 응답에서 검토 배열 6개를 루트에 배치해 중첩 구조를 줄였다. 서버는 기존 `reviewNotes` 형식으로 복원하므로 DB·검토 UI·공통 검증의 계약은 유지한다. 프롬프트 버전은 `3.5-comparison-review-contract`이며 기존 비교 캐시와 구분된다.
- 같은 페이지 내부의 위젯 추가·기존 제외 해제도 추가 범위라는 지시와 분류 필드 설명을 명확히 했다. 모델의 판정을 서버가 임의로 변경하지 않는다.
- 다른 필드가 유효하고 검토 배열만 누락된 비교 응답은 미완성 검토 초안으로 보존한다. 누락 배열을 편집 가능한 목록으로 마련하면서 **누락된 항목을 대조하라는 필수 확인**을 추가한다. 근거 출처는 만들지 않으며, 빈 목록을 해당 사항 없음의 확정으로 취급하지 않는다.
- 원본 응답·추가 시간·원래 판정은 보존한다. 상충하는 값, null 또는 잘못된 타입, 필수 본문 누락, 잘린 JSON은 이 처리로 통과시키지 않는다.
- 미완성 초안은 `AI_RESPONSE_INCOMPLETE`로 표시하고 예약 Credit을 해제한다. 실제 서비스 차감은 0이며 정상 결과 캐시에는 넣지 않는다. 제공자 비용·사용량의 불명 상태는 별도로 유지한다.
- 일반 검토 화면에서 누락 항목 확인 사유·근거, 범위 판정을 보완한다. 원래 필수 확인 항목을 삭제해도 서버는 원본 기준의 해소 근거를 요구한다. 오류·근거 누락 상태에서는 고객 승인으로 진행할 수 없다.

## 검증

- Backend 71개·Frontend 14개 테스트 통과, 건너뜀 없음. 이후 추가한 식별자 충돌·동일 실행 재사용 검사는 관련 테스트를 다시 실행해 통과했다.
- 양쪽 Production 빌드·TypeScript 검사·lint 통과.
- 실제 저장된 실패 응답의 필드·값을 재생해 미완성 초안 보존, 원본·판정·시간 유지와 추가 제공자 호출 없음을 확인했다. 외부 요청은 모의 응답으로 대체했다.
- 기존 답변 4개·출처 19개 격리 시나리오는 추정 입력 6,612 + 응답 상한 1,388로 요청 예산 8,000 안에 들어간다. 수치는 UTF-8 크기 기반 추정이며 실제 모델 토큰 수가 아니다.
- 격리 PostgreSQL에서 0 Credit, 캐시 제외, 동일 실행 재사용, 누락 확인 없는 확정 차단, 기존 승인 문서 불변을 확인했다.
- 로컬 브라우저에서 JSON 편집 없이 범위 판정·출처·확인 사유를 입력하고 저장했다. 서버 검증은 오류·경고·검토 필요 모두 0이 되었으며, 원래 `IN_SCOPE` 분석과 검토한 `OUT_OF_SCOPE` 후보가 별도로 남았다. 추가 시간 2/0/1/1, 기준 800,000원·8일, 실제 차감 0 Credit은 유지됐다.

이번 작업의 실제 Groq 요청은 **0회**다. 이전에 허용받은 총 2회 제한은 그대로 유지한다. 새 wire 계약에 대한 실제 모델 생성 성공은 추가 호출 없이 확인할 수 없다. 운영 DB 쓰기·마이그레이션·환경변수 변경은 없으며, 기존 실패 이력은 소급해 성공으로 바꾸지 않았다.
