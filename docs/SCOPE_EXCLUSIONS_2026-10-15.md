# ScopeFlow 원문 제외 조건·Scope 제외 범위 연결

작성일: 2026-10-15. 기준: `ScopeFlow-Scope-Exclusions-Spec.md`.

## 구현 범위

원문·저장 답변 → 기존 공통 Context → 항목별 담당자 검토 → Scope 초안/고객 문서 → 변경 승인 후 다음 버전을 연결했다. 기존 Context·Rule Validator·Scope·승인 서비스를 확장했고, 별도 AI 서비스·새 테이블·의존성·유료 호출은 추가하지 않았다.

- 원문 4개(결제·회원가입·관리자·외부 연동)와 답변의 별도 서버 제외를 개별 후보로 제안한다. 근거 원문·답변 ID/버전/인용을 보존한다. 같은 의미의 제한된 동의어는 근거를 합쳐 제안하고 이용료/수수료와 개발 제외는 합치지 않는다.
- 새 후보는 기본 `pending`이며 담당자 확인으로 `active`가 된다. active는 고객 승인 완료와 별개다. 담당자/템플릿/AI 추정과 고객 원문/답변을 구분하고, 자료 제공·정적 호스팅·같은 페이지를 임의의 개발 제외로 확대하지 않는다.
- 원문·답변의 명시 조건은 Scope 확인 전에도 포함 요구사항과의 충돌 검사에 사용한다. 단순 문구·본문 첨부나 공통 추가 기능 제외 문장으로 RV-011을 통과할 수 없다.
- Scope 생성/수정 폼에서 제목·설명·상태·출처·근거·사유를 검토한다. 현재 리비전 전체 확인, 직접 추가(담당자/템플릿), 중복 대상 선택, 후속 고객 근거를 연결한 해제, 잘못된 후보의 사유 있는 기각을 지원한다. 행 자체를 조용히 삭제하지 않는다.
- 불명확한 제안을 확인하려면 담당자 판단 사유가 필요하다. 고객이 실제로 명시한 조건을 기각하려면 동일 의미의 유지할 중복 항목이 있어야 하며, 후속 조건으로 해제하려면 실제 고객 요청/저장 답변의 긍정 변경 근거와 사유가 필요하다. ‘제외하지 않는다’만으로 새 포함 요구사항을 확정하지 않는다.
- 신규 AI 결과는 기존 active 목록을 자동 대체하지 않는다. 추가 제외는 pending 제안으로 남기고 기존 AI 검토 화면과 비교한다. 적용된 추출 결과는 고객 원문/답변 origin과 별개로 실제 AI 실행 ID를 내부 provenance에 연결한다.
- 승인 전 pending 목록은 초안으로 저장할 수 있지만 승인 요청/확정은 차단한다. 목록/문서 불일치와 포함 기능 충돌도 차단한다. RV-007/RV-011과 기존 한국어 필드 오류/입력 보존을 재사용한다.
- 고객 문서는 저장한 active 제목·설명만 사용한다. 담당자 미리보기·고객 승인 대기/완료·과거 버전은 같은 Scope document를 렌더링한다. 내부 근거·상태·검토 로그·AI 실행 ID는 고객 제외 목록에 넣지 않는다.
- 변경 승인 전에는 기존 제외를 유지한다. 관리자 추가 변경을 담당자가 검토하고 고객이 승인하면 새 버전에서 관리자 제외만 superseded로 남긴다. 다른 제외 항목과 이전 승인 문서는 보존한다. 다른 변경 선승인 시 기존 기준 변경 검사로 재비교한다.

## 저장·API 계약

- 정규화/제안/편집 검사는 `Backend/src/lib/scope-exclusions.ts`, 공통 Context 전달은 `ai-context.service.ts`, 저장·승인·후속 버전은 기존 `workflow.service.ts`에서 처리한다.
- 항목별 검토 상태는 기존 `Scope.validationReview.exclusionReview` JSON에 `{ revision, contextFingerprint, items }`로 저장한다. actor·시각·사유 및 before/after는 기존 감사 로그의 `SCOPE_EXCLUSIONS_REVIEWED`에 연결한다. 해당 버전의 내부 상세 화면에서도 근거·사유·당시 상태를 확인할 수 있다.
- 고객 원문 조건을 별도 DB에 복제하지 않는다. 기존 `Project.contextReview.excludedScope`는 유지하며, 적용된 AI 추출의 실행 참조만 확장했다. 실제 원문/답변은 기존 sources를 사용한다.
- 최신 편집 기준은 내부 프로젝트 조회의 `aiContext.scopeExclusions`와 `aiContext.sources`로 제공한다. Scope `scope.create`/`scope.edit` 명령 및 기존 POST/PATCH Scope API에 `exclusions: { revision, contextFingerprint, items }`를 전송한다. 명령 폼의 JSON 문자열은 서버에서 검증한다.
- Scope 수정에는 기존 `candidateRevision`도 보낸다. 서버는 프로젝트 lock 안에서 권한·출처·항목 리비전·현재 원문/답변/포함 조건 fingerprint를 확인한다. sourceRefs/origin/인용·추출 실행 참조/기존 항목 ID를 클라이언트가 임의 변경할 수 없다. 새 담당자 조건을 고객 조건으로 위장하거나 다른 프로젝트 출처를 사용할 수 없다.
- 공개 document의 `exclusions`는 `{ title, description }[]`만 포함한다. 기존 `excluded: string[]`는 같은 목록에서 만든 호환 projection이며 독립 편집 저장소가 아니다. 고객 문서 컴포넌트는 구조 목록을 우선 사용하고, 과거 문서에는 기존 문자열 목록을 그대로 표시한다.
- 새 제외 검토 모델에 필요한 DB migration은 없다. 이전 작업의 `0003`~`0006` 적용 요구는 여전히 유효하다. 이번에는 격리 테스트 DB만 사용했고 일반 로컬/운영 DB·환경변수·배포 상태는 변경하지 않았다.

## 기존 문서 보존

- 자유 문구의 구분자를 자동 분리하여 확정 조건으로 만들지 않는다. 과거 문구를 원형 그대로 담당자 후보로 표시하며 없는 고객 출처를 만들어 붙이지 않는다.
- 미검토 과거 초안을 일반 저장할 때 기존 제외 문구를 새 빈 목록으로 조용히 교체하지 않는다. 기존 문구는 document에 보존하고 새로운 검토 후보/상태는 validationReview에 저장한다. 관련 검토가 끝나기 전 승인 요청은 보류한다.
- 이미 승인된 문서와 발급 문서는 조회로 수정하지 않는다. 보완이 필요하면 기존 회수·재발급 또는 변경 요청·새 버전을 이용한다. 문구/상태 조회와 항목 편집에는 AI 호출/Credit 차감이 없다.

## 의미 추출·미검증 범위와 운영

- 보조 추출은 QA의 결제/회원가입/관리자/외부 연동/별도 서버 및 일부 명시 표현에 한정된 결정적 제안이다. 자유 문장의 모든 의미·새 업종/기능·복합 부정을 자동 판별하지 않는다. 기존 AI의 근거 연결 제안과 담당자/Q&A 검토를 계속 사용한다.
- 알려진 기능의 동의어와 명백한 충돌은 기존 Validator의 구조 속성에 연결한다. 임의의 제목·설명 문구 변경은 의미 자동 동등성을 보장하지 않으며, 원문·근거와 담당자 사유를 확인해야 한다. AI 추정은 고객 명시 조건으로 자동 승격하지 않는다.
- 실제 Groq 품질/유료 호출, 모바일 실기기, 실제 음성 스크린리더, 모든 편집/해제 조합의 브라우저 순회는 미실행이다. 고객 승인 완료/관리자 변경 버전은 서비스·DB 검사이며 해당 과정을 새 브라우저 E2E로 반복하지 않았다.
- Prisma/pg의 기존 동시 query deprecation 경고가 있었지만 검사 실패는 없었다. 새 드라이버·SDK·서버·PDF 기능·과금 정책은 추가하지 않았다.
- 커밋·푸시·Vercel 배포·운영 migration은 하지 않았다. 이전 미커밋 작업을 보존했다. 검증용 계정·토큰·로그는 ignored `test-results`에 두며 이 문서에 자격 증명은 기록하지 않는다.
- 검증을 위해 실행한 Frontend/Backend 서버, 전용 Chrome 탭 2개와 격리 PostgreSQL(55436)은 종료했다. 테스트 데이터·로그·화면 증거는 보존했다.
